# 에너지 뉴스 트렌드 분석 CLI (energy-news-cli)

전기신문(electimes.com)의 에너지 뉴스를 **RSS와 크롤링 두 방법**으로 모으고 SQLite에 원본(raw)과 정제본(clean)으로 나눠 저장한다. AI로 기사마다 요약하고 기간·카테고리별로 종합 분석한 뒤, 차트와 리포트를 만들어 CSV·JSONL·Excel로 내보낸다. 모든 기능은 `python main.py <명령>` 하나로 실행한다.

과제: AI Native Term Project `[Project B] AI 뉴스 트렌드 및 종합 분석 리포트`

```
fetch ──▶ raw_news ──clean──▶ clean_news ──summarize──▶ summaries
(RSS·크롤링)  (받은 그대로)     (검증·정규화·중복 처리)       (기사별 AI 요약)
                                    │
                                    ├──analyze──▶ analyses (기간·카테고리 AI 종합 분석)
                                    │
                                    └──report / export / list / show
                                       (차트 PNG, 리포트 MD·TXT, CSV·JSONL·XLSX, 조회)
```

## 1. 빠른 시작

### 1.1 설치

Python 3.10 이상이 필요하다. 개발과 실행은 3.14에서 했고, 3.10은 문법과 표준 라이브러리 호환만 점검했다.

```
python -m venv .venv
.venv\Scripts\activate          (macOS·Linux: source .venv/bin/activate)
pip install -r requirements.txt
```

필요한 패키지: `requests`, `beautifulsoup4`, `python-dotenv`, `matplotlib`, `openpyxl`

### 1.2 API 키 설정

`.env.example`을 `.env`로 복사한 뒤 값을 채운다. `.env`는 `.gitignore`에 있어서 저장소에 올라가지 않는다.

```
copy .env.example .env          (macOS·Linux: cp .env.example .env)
```

| 환경변수 | 내용 |
|---|---|
| `CODYSSEY_API_KEY` | 기관 AI API 키 (OpenAI 호환) |
| `CODYSSEY_BASE_URL` | API 주소 (예시 파일에 기본값) |
| `CODYSSEY_MODEL` | 모델 이름 (기본 `gemini-3-flash`) |

`config.json`에는 키 값이 아니라 **환경변수 이름**만 적혀 있다(`ai.env`). 키가 없으면 AI를 쓰는 명령(summarize, analyze)만 필요한 변수 이름을 안내하고 멈추고, 나머지 명령은 그대로 동작한다.

### 1.3 전체 흐름 실행

```
python main.py fetch --since 2026-10-06      # 기준일 이후 수집 (날짜는 실행일 3~4일 전으로)
python main.py clean                         # 검증·정규화·중복 처리
python main.py summarize                     # 요약 안 된 기사만 AI 요약
python main.py analyze                       # 전체 기간·카테고리 AI 분석
python main.py analyze --category 전력,원자력  # 카테고리 조건 분석
python main.py report                        # 차트 3개 + 리포트(콘솔·MD)
python main.py export --status summarized    # CSV·JSONL·XLSX
python main.py list --keyword HVDC           # (보너스) 목록
python main.py show 16                       # (보너스) 상세, list에 나온 번호
```

`--since` 날짜가 멀수록 기사 수와 AI 요약 시간이 늘어난다. 10-10에 `--since 2026-10-06`으로 실행했을 때 기사 68건, 수집 약 3분(165초), 요약 약 6분(5분 41초)이었다([docs/실행_기록.md](docs/실행_기록.md)).

### 1.4 테스트 (네트워크·API 없음)

```
python -m unittest discover -s tests -t .
```

테스트 142개. 가짜 HTTP 세션과 메모리 DB를 쓰기 때문에 사이트와 AI API에 요청하지 않는다.

## 2. 요구사항 충족표

"과제 원문"은 과제 문서 4절(기능 요구 사항)·5절(보너스)·6~7절(환경·제약)의 요구를 줄여 옮긴 것이다.

### 2.1 필수

| 과제 원문 | 이 프로젝트 구현 | 확인 방법 |
|---|---|---|
| argparse 서브커맨드 CLI, 필수 6개(fetch·clean·summarize·analyze·report·export) | 6개 + 보너스 2개(list·show). `news_cli/cli.py` | `python main.py --help` |
| 서브커맨드별 옵션(--limit, --category, --date, --format 등) | `--limit`, `--category`, `--since`, `--date-from`·`--date-to`, `--format`, `--status`, `--items`, `--top` 등 (3절) | `python main.py <명령> --help` |
| 수집 방법 1: 공개 뉴스 API 또는 RSS | 섹션 RSS 피드 3개(에너지·탄소중립·전기경제). `news_cli/collect/rss.py` | `fetch --method rss` |
| 수집 방법 2: 크롤링(BeautifulSoup 또는 Selenium) | 세부 카테고리 10개의 목록 페이지 + 기사 페이지를 BeautifulSoup으로 해석. `news_cli/collect/crawler.py` | `fetch --method crawl` |
| HTTP 타임아웃과 오류 처리 | 타임아웃 10초, 연결 실패·429·5xx는 2초·4초 기다려 재시도, 그 밖의 4xx는 재시도 없이 기록, robots.txt 확인. `news_cli/collect/http_client.py` | 테스트 `test_http_fetch`(404는 재시도 안 함, 5xx 재시도, 타임아웃, robots.txt 금지·연결 불가·Crawl-delay) |
| raw 저장소에 수집 시각·소스·수집 방법과 함께 저장 | `raw_news`: source, method(`rss`·`crawl`), channel, fetched_at, payload(받은 그대로 JSON) | `show ID`의 수집 이력 |
| 정제: 필수 필드 검증, 텍스트 정규화, 날짜 통일, 결측값 처리 | 필수 4개 필드가 없으면 `rejected`. 태그·엔티티·바이라인 제거, 날짜 4가지 형식 → 한국 시간 `YYYY-MM-DD HH:MM:SS`, 기자 없음 → `미상`, 본문 없음 → 요약문으로 대체 또는 `no_body`. `news_cli/collect/cleaner.py` | 테스트 `test_cleaner_rules` |
| 중복 처리 정책 skip/upsert | config `clean.duplicate_policy`(기본 skip), 실행마다 `clean --policy`로 바꿀 수 있음. upsert는 빈 값으로 덮어쓰지 않음 | 테스트 `test_clean_db`, 실행 기록 5절 1~4번 |
| clean 저장소에 별도 저장 | `clean_news` 테이블(기사 1건 = 1행) | `list` |
| AI API로 본문 요약 | 기관 API(OpenAI 호환)를 `requests`로 직접 호출. 3문장·300자 이내 요약 + 키워드 3~5개. `news_cli/ai/summarizer.py` | `summarize`, `show ID` |
| 요약 대상 선택 --all, --id, --unsummarized | 셋 다 지원(기본 `--unsummarized`), `--limit`, `--force` 추가 | `summarize --help` |
| API 실패 시 로깅 후 스킵, 이미 요약된 뉴스는 기본 스킵 | 한 건당 최대 3번 시도 후 ERROR 로그·`ai_errors` 기록·다음 기사로. 이미 요약된 기사는 `--force`가 없으면 건너뛰고 건너뛴 수를 알림 | 실행 기록 5절 5~8번 |
| 조건별(기간, 카테고리) 종합 분석 | `analyze --date-from --date-to --category` | 실행 기록 4절 4번 |

| 분석 결과 별도 저장, 리포트에 활용 | `analyses` 테이블. `analyze --history`·`--show-id`로 다시 보기(AI 호출 없음), 리포트는 조건이 같은 최신 분석을 싣는다 | `report` |
| matplotlib 차트 2종: 카테고리별 뉴스 수, 일자별 수집 추이 | 2종 + 요약 상태 차트. 일자별은 발행일·수집일 선 2개. `news_cli/output/charts.py` | `output/charts/*.png` |

### 2.3 과제에 없지만 더한 것

| 추가 | 이유 |
|---|---|
| `fetch --since YYYY-MM-DD` | 카테고리마다 최신 N건만 받으면 카테고리별 기사 수가 모두 같아진다. 기간 기준으로 모아야 "카테고리별 뉴스 수" 차트가 의미를 가진다(4.4절) |
| 요약 상태 차트 | 요약 완료·실패·본문 없음 비율을 한눈에 본다 |
| `analyze --history`·`--show-id` | 저장된 분석을 AI 호출 없이 다시 본다 |
| `clean --rebuild` | 정제 규칙을 고친 뒤 사이트에 다시 요청하지 않고 raw에서 다시 만든다 |

## 3. 명령 사용법

공통 옵션(명령 뒤에 붙임): `--config config.json`, `--db data/news.db`, `-v`(DEBUG 로그도 콘솔에). 종료 코드: 0 성공, 1 실행 오류(설정·DB·모든 요청 실패·대상 없음), 2 잘못된 옵션, 130 사용자 중단(그때까지 저장한 내용은 유지).

| 명령 | 주요 옵션 | 하는 일 |
|---|---|---|
| `fetch` | `--source electimes`(지금은 이 하나만 됨, 다른 값은 옵션 오류), `--method {rss,crawl,all}`(기본 all), `--feed`, `--category`, `--since YYYY-MM-DD`, `--limit`(기본 10, `--since`면 50), `--pages`(기본 1, `--since`면 5), `--recrawl` | RSS 수집 + 세부 카테고리 목록·기사 크롤링 → `raw_news` |
| `clean` | `--policy {skip,upsert}`, `--limit`, `--rebuild` | raw → 검증·정규화·카테고리·중복 처리 → `clean_news` |
| `summarize` | `--unsummarized`(기본) \| `--all` \| `--id 1 2 3`, `--limit`, `--force` | 기사별 AI 요약 → `summaries` |
| `analyze` | `--date-from`, `--date-to`, `--category`, `--items trends,keywords,common_diff,implications`(기본 4개 모두, 2개 이상), `--max-articles`(기본 40), `--history`, `--show-id N` | 조건별 AI 종합 분석 → `analyses` |
| `report` | `--date-from`, `--date-to`, `--category`, `--top`(기본 5), `--format {md,txt}`, `--analysis-id`, `--output` | 차트 PNG 3개 + 리포트(콘솔·파일). AI를 부르지 않음 |
| `export` | `--format csv,jsonl,xlsx`, `--status`, `--date-from`, `--date-to`, `--category`, `--include-body`, `--output-dir` | 기사 + 최신 요약 → 파일. 본문은 `--include-body`일 때만 |
| `list` | `--category`, `--date-from`, `--date-to`, `--keyword`, `--status`, `--page`, `--size` | (보너스) 최신 발행순 목록 |
| `show` | `ID`, `--full` | (보너스) 기사 상세 |

## 4. 설계 근거

### 4.1 뉴스 소스: 전기신문

에너지 전문지 5곳을 비교했다(2026-10-10 확인, 설계서 2.1절).

- 전기신문을 고른 이유: 섹션 RSS가 최신 상태로 갱신되고, **세부 카테고리 목록 필터가 서버에서 실제로 적용된다**(전력 목록과 태양광 목록이 서로 다름). 기사 페이지에도 세부 카테고리가 메타 태그로 있다.
- 처음 고른 투데이에너지는 세부 카테고리 목록에 항상 전체 기사가 나와서(필터가 적용되지 않음) 카테고리 근거가 약해 바꿨다. 나머지는 RSS가 멈춰 있거나 없었다.
- robots.txt는 `/admin/`만 금지한다. 사이트 저작권 정책이 승낙 없는 복제·배포를 금지하므로 **기사 본문은 로컬 DB에만 두고 저장소에 올리지 않는다**. 리포트·내보내기에는 제목·링크·직접 만든 요약과 분석만 넣는다. 테스트 샘플 HTML도 실제 구조를 본뜨고 본문은 가짜 문장으로 채웠다.

### 4.2 저장소: SQLite, raw와 clean 분리

- SQLite는 파이썬 표준 라이브러리로 쓸 수 있고 파일 하나라 설치가 필요 없다. 기간·카테고리 조건 조회, 중복 키(UNIQUE), 집계를 SQL로 바로 할 수 있다. JSONL 파일은 조건 조회와 같은 기사 갱신(upsert)이 불편하다.
- 테이블 6개: `raw_news`, `fetch_log`(수집 실행 기록), `clean_news`, `summaries`, `analyses`, `ai_errors`. raw와 clean을 나눈 이유는 6.3절.
- 기사 하나를 구분하는 키는 전기신문 기사 번호(`idxno`)다. raw는 `UNIQUE(method, article_key, payload_hash)`라 완전히 같은 내용은 두 번 쌓이지 않고, clean은 `article_key`가 UNIQUE다.

### 4.3 모듈 구조: 역할별 패키지, 테이블로 연결

- 코드는 `news_cli/` 아래 `collect/`(역할 1: 수집·정제), `ai/`(역할 2: 요약·분석), `output/`(역할 3: 차트·리포트·내보내기·조회), 공통(`cli.py`, `settings.py`, `logger.py`, `db.py`)으로 나눴다. 코드 패키지 `news_cli/output/`은 실행 결과 폴더인 최상위 `output/`과 다르다.
- 역할끼리는 함수 호출이 아니라 **DB 테이블**로 연결된다. 역할 1은 `clean_news`를 채우고, 역할 2는 그것을 읽어 `summaries`·`analyses`를 채우고, 역할 3은 읽기만 한다. 그래서 다른 역할의 코드를 몰라도 각자 개발하고 테스트할 수 있다.
- HTTP 모듈 이름을 `http_client.py`로 한 것은 표준 라이브러리 `http`와 이름이 겹치지 않게 하려는 것이다.

### 4.4 수집 방식: 기간 기준(`--since`)

- 처음에는 카테고리마다 최신 N건(`--limit`)만 받았다. 실제로 돌려 보니 10개 카테고리가 모두 5건이 되어 "카테고리별 뉴스 수" 차트가 아무것도 보여 주지 못했다(실행 기록 7.1절).
- 그래서 `--since`를 더했다. 그 날 이후 발행된 기사만 받고, 목록은 최신순이므로 기준일보다 오래된 기사가 보이면 다음 쪽을 보지 않는다. `--limit`·`--pages`는 상한으로 남기고, 상한 때문에 기간 안 기사를 다 받지 못했을 수 있으면 WARNING을 남긴다.
- 결과: 같은 기간(10-06~10-10)에 전력 14건, 원자력 6건, 풍력 1건처럼 분야별 기사량 차이가 드러났다.

### 4.5 카테고리 정하기

`site`(사이트의 세부 카테고리, 단 설정한 10개 안일 때만) → `keyword`(제목에 카테고리 키워드) → `default`(`기타`) 순서로 정하고, 근거를 `category_source`에 남긴다. 설정 밖의 사이트 분류(산업정책, 칼럼 이름 등)를 그대로 쓰면 차트에 우리가 정하지 않은 이름이 섞여서 이렇게 바꿨다. 사이트가 준 원래 값은 raw에 그대로 남아 있다.

### 4.6 API 키와 설정

- 과제는 "config.json으로 API 키 관리"와 "API 키는 코드에 쓰지 않고 환경변수 또는 설정 파일로 관리"를 함께 요구한다.
- 그래서 `config.json`에는 키를 읽을 **환경변수 이름**(`ai.env.api_key = "CODYSSEY_API_KEY"`)을 두고, 키 **값**은 `.env`에 둔다. config.json은 저장소에 올려 팀이 공유하고, `.env`는 각자 자기 키로 만든다. 설정 파일을 공유하거나 커밋해도 키가 노출되지 않는다.
- 키 값은 요청 헤더에만 넣고 로그·오류 메시지·DB·출력 파일에 쓰지 않는다. 실제 실행 뒤 45개 파일에서 키 값이 나오지 않는 것을 확인했다.

### 4.7 AI 연동: 기관 API 제약에 맞춘 호출

기관 API는 OpenAI 호환(`/v1/chat/completions`)이지만 일부 기능을 지원하지 않는다. 그래서 공식 SDK 대신 `requests`로 요청 본문을 직접 만든다(`news_cli/ai/client.py`).

| 제약 | 대응 |
|---|---|
| JSON 모드(`response_format`) 미지원 | 프롬프트에 출력 형식 예시와 "JSON 객체 하나만" 지시. 응답에서 코드펜스·앞뒤 설명을 건너뛰고 첫 JSON 객체를 읽는다. 못 읽거나 필수 키가 없으면 "JSON만 다시" 문구를 붙여 재요청 |
| 모델의 사고 토큰이 `max_tokens`에 포함됨 | `max_tokens`를 보내지 않는다(보내면 답이 잘리거나 빈다). 길이는 프롬프트로 제한 |
| 긴 입력에서 간헐적 400 | 요약은 본문 4,000자 → 2,000자, 분석은 기사별 300자 → 150자로 줄여 재요청 |
| 타임아웃·연결 실패·429·5xx | 2초·4초 기다렸다가 재요청 |
| 401·403(키 오류) | 재요청하지 않고 명령을 멈춘다(남은 기사도 같은 이유로 실패하므로) |

재요청은 모두 합쳐 **한 건당 최대 3번**이다. 무한 재시도는 하지 않는다.

### 4.8 프롬프트 설계

- 역할을 정해 준다(요약: "에너지 산업 뉴스 편집자", 분석: "에너지 산업 동향 분석가").
- **"주어진 기사에 없는 사실·수치는 쓰지 않는다"**를 시스템·사용자 프롬프트 양쪽에 둔다(환각 줄이기).
- 요약은 "3문장 이내, 300자 이내, 수치·기관명·지명은 그대로", 키워드는 "고유명사·기술 용어 우선, '에너지'·'정부' 같은 일반어는 피함".
- 분석 입력은 기사 본문이 아니라 `[ID] 발행일 | 카테고리 | 제목 / 요약`이다(요약이 없는 기사는 본문 앞 300자를 쓰고 WARNING을 남긴다). 기사 40건을 넣어도 입력이 짧고, 트렌드마다 근거 기사 ID를 받을 수 있다.
- 모델이 돌려준 근거 ID 중 **입력에 없는 번호는 버리고** WARNING을 남긴다. 리포트에는 남은 ID의 기사 제목과 링크를 함께 싣는다. 독자가 근거를 직접 확인할 수 있게 하려는 것이다.

## 5. 오류 처리 정책

원칙: **한 건의 실패가 전체를 멈추지 않는다.** 실패는 로그와 DB(`fetch_log`, `ai_errors`, raw의 `status`·`note`)에 남기고 다음으로 넘어간다. 다만 다시 해도 똑같이 실패할 것이 분명한 경우(키 오류, 잘못된 옵션)는 바로 멈추고 이유를 알린다.

| 상황 | 처리 | 프로그램 |
|---|---|---|
| HTTP 타임아웃(10초)·연결 실패 | 2초·4초 기다려 2회 재시도 후 WARNING, 실패 건수 기록 | 계속 |
| HTTP 404·403 등 4xx (429 제외) | 재시도 없이 기록 (다시 해도 같음) | 계속 |
| HTTP 429·5xx | 재시도 | 계속 |
| robots.txt 금지 경로 | 요청하지 않음 | 계속 |
| robots.txt를 읽지 못함 | 그 실행에서는 아무 요청도 하지 않음(404면 제한 없음으로 봄) | 계속(수집 0건) |
| RSS XML 해석 실패 | 그 피드만 ERROR, 다른 피드는 진행 | 계속 |
| 기사 페이지 구조 변경(본문 없음) | raw에는 저장, clean에서 요약문으로 대체하거나 `no_body` | 계속 |
| 정제 실패(필수 필드·날짜) | raw를 `rejected`로 표시하고 이유를 note에 | 계속 |
| AI 호출 실패(타임아웃·429·5xx·400·형식 오류) | 한 건당 최대 3번 후 `ai_errors` 기록, 그 기사만 건너뜀. 다음 `summarize` 때 다시 시도 | 계속 |
| AI 키 오류(401·403) | 재요청 없이 ERROR, 그때까지 한 요약은 유지 | 그 명령만 종료(1) |
| API 키 없음 | 필요한 환경변수 이름만 안내(값은 출력 안 함) | 그 명령만 종료(1) |
| 분석·리포트·내보내기 대상 기사 없음 | WARNING, AI 호출이나 파일 생성 없음 | 그 명령만 종료(1) |
| 리포트 조건과 같은 분석 없음 | 리포트는 만들고 그 조건의 `analyze` 명령을 안내 (AI를 대신 부르지 않음) | 계속 |
| 한글 폰트 없음 | WARNING, 기본 폰트로 차트 생성 | 계속 |
| 없는 ID·쪽, 날짜 역순, 모르는 카테고리·형식, 분석 항목 1개 | ERROR로 이유 안내 | 그 명령만 종료(2) |
| Ctrl+C | 중단 직전까지 받은 것을 커밋하고 끝낸다(평소에도 수집은 채널마다, 요약은 기사마다 커밋). 다시 실행하면 받은 것·요약한 것은 건너뛴다 | 종료(130) |

이 정책을 실제 데이터로 확인한 결과는 [실행 기록 5절](docs/실행_기록.md)에 있다(없는 모델로 404, 닿지 않는 주소로 연결 실패 3회 후 기록, 다시 실행해 복구, 키 없음, 틀린 키 401 등 14가지).

## 6. 과제 목표 5가지 설명

### 6.1 API·RSS 방식과 크롤링 방식의 장단점

| 항목 | RSS (`news_cli/collect/rss.py`) | 크롤링 (`news_cli/collect/crawler.py`) |
|---|---|---|
| 형식 | 정해진 XML이라 해석이 안정적 | HTML 구조에 기대므로 사이트 개편 때 깨질 수 있음 |
| 내용 | 섹션마다 최신 20건, 본문 대신 요약문 | 본문 전체, 쪽을 넘겨 지난 기사까지 |
| 분류 | 상위 섹션(에너지·탄소중립·전기경제)까지만 | 세부 카테고리(전력·태양광 등 10개) |
| 부담 | 요청 1번에 20건 | 기사마다 요청 1번이라 느리고 서버 부담이 큼 → 2초 지연 필수 |
| 정책 | 배포용으로 공개된 피드 | robots.txt·이용 정책 확인 필요 |

이 프로젝트는 둘을 보완적으로 쓴다. RSS로 최신 기사를 빠르게 찾고, 크롤링으로 본문과 세부 카테고리를 채운다. RSS로 찾은 기사도 기사 페이지를 크롤링하면 본문과 사이트 카테고리를 얻는다. 실제 실행에서 RSS 60건과 카테고리 목록이 겹쳐 기사 68건이 됐고, 그중 60건은 두 방법으로 함께 들어와 하나로 합쳐졌다.

### 6.2 외부 데이터 수집과 오류 처리

`news_cli/collect/http_client.py`의 `HttpClient.get()`이 모든 사이트 요청을 맡는다.

1. robots.txt에서 금지된 주소인지 확인한다(`allowed()`). 금지면 요청하지 않는다.
2. 직전 요청에서 2초(또는 Crawl-delay)가 지나지 않았으면 기다린다.
3. 타임아웃 10초로 요청한다.
4. 결과에 따라 나눈다. 성공은 그대로 돌려준다. 404·403 같은 4xx(429 제외)는 재시도해도 같으므로 바로 실패로 기록한다. 타임아웃·연결 실패·429·5xx는 2초·4초 기다려 최대 2번 더 시도한다.
5. 실패해도 예외로 멈추지 않고 `FetchResult(ok=False, error=…)`를 돌려준다. `fetcher.py`가 채널별로 요청·성공·실패·저장 수를 `fetch_log`에 남기고 다음 기사로 넘어간다. 이 기록이 리포트의 "수집 성공률"이 된다.

AI API 쪽도 같은 원칙이다(4.7절, 5절).

### 6.3 raw와 clean을 나눠 저장하는 이유

- **다시 처리할 수 있다.** 정제 규칙을 고쳐도 사이트에 다시 요청하지 않고 raw에서 clean을 새로 만든다(`clean --rebuild`). 실제로 카테고리 규칙을 바꾼 뒤 이렇게 반영했다. 서버 부담과 차단 위험이 줄어든다.
- **추적할 수 있다.** clean의 값이 이상하면 raw의 원래 응답(payload)과 수집 시각·방법을 보고 수집 문제인지 정제 문제인지 가린다. `show ID`가 기사마다 raw 수집 이력을 보여 준다.
- **역할이 나뉜다.** raw는 "받은 그대로", clean은 "분석에 쓸 수 있게 검증된 것"이다. 요약·분석·리포트는 clean만 읽는다.

단계별 역할:

| 단계 | 하는 일 | 저장 |
|---|---|---|
| fetch | 받은 값을 손대지 않고 저장(수집 시각·소스·방법·채널 포함) | `raw_news`, `fetch_log` |
| clean | 같은 기사의 raw 합치기 → 필수 필드 검증 → 텍스트 정규화 → 날짜 통일 → 결측값 처리 → 카테고리 → 중복 정책 | `clean_news` (raw는 `cleaned`·`rejected`·`duplicate` 표시) |
| summarize·analyze | clean을 읽어 AI 결과 저장 | `summaries`, `analyses`, `ai_errors` |
| report·export·list·show | 읽기만 | 파일 |

### 6.4 AI API로 요약·분석하는 흐름

요약(`news_cli/ai/summarizer.py`), 기사 1건마다:

1. 대상 고르기: 기본은 요약 전·요약 실패 기사. 이미 요약된 기사와 본문 없는 기사는 건너뛴다.
2. 입력 만들기: 제목 + 본문 앞 4,000자 (400 응답에 대비해 2,000자 판도 준비).
3. 호출(`AIClient.ask_json`): 시스템 프롬프트 + 사용자 프롬프트를 보낸다(`max_tokens` 없음).
4. 응답 처리: 첫 JSON 객체를 꺼내 `summary`가 있는지 검사하고, 키워드를 정리한다(공백·`#`·중복 제거, 최대 5개).
5. 저장: `summaries`에 새 행, 기사 상태를 `summarized`로 바꾸고 바로 커밋한다.
6. 실패 시: 4.7절 표대로 최대 3번 시도한 뒤 `ai_errors`에 기록하고 상태를 `summary_failed`로 둔다. 다음 기사로 넘어간다.

분석(`news_cli/ai/analyzer.py`)은 조건에 맞는 기사 중 최신 40건의 `ID·날짜·카테고리·제목·요약`(요약이 없으면 본문 앞부분)을 한 번에 보내고, 요청한 항목이 모두 있는지와 근거 ID가 입력에 있는지 검사한 뒤 `analyses`에 저장한다.

### 6.5 집계와 시각화 과정

1. 조건(기간·카테고리)에 맞는 기사와 기사별 최신 요약을 SQL로 읽는다(`news_cli/output/common.py`).
2. 집계(`news_cli/output/stats.py`):
   - 카테고리별·상태별 기사 수
   - 일자별 기사 수: 발행일 기준과 수집일 기준. 첫날부터 마지막 날까지 빈 날은 0으로 채운다
   - TOP N: 카테고리, 키워드(띄어쓰기·대소문자만 다른 표기는 합침), 기자(`미상` 제외). 같으면 이름순
   - 품질 지표 7개(7절)
3. 차트(`news_cli/output/charts.py`): matplotlib `Agg` 백엔드(화면 없이 그림)로 설치된 한글 폰트를 골라 PNG 3개를 저장한다.
   - 카테고리별 가로 막대
   - 일자별 선 2개
   - 요약 상태 막대
4. 리포트(`news_cli/output/report.py`): 집계 결과, 조건이 같은 최신 AI 분석, 차트 경로를 묶어 콘솔(TXT)에 출력하고 MD 또는 TXT 파일로 저장한다.

## 9. 설계 질문과 답

### 9.1 원리

**Q1. RSS가 있는데 왜 크롤링도 하나요?**
RSS는 섹션 3개의 최신 20건과 요약문만 준다. 세부 카테고리(전력·태양광 등)와 본문이 없다. 크롤링으로 세부 카테고리 목록과 기사 본문을 받아 채운다. 과제가 두 방법을 모두 요구하기도 하지만, 실제로도 둘이 서로 모자란 부분을 메운다(6.1절).

**Q2. raw와 clean을 왜 나눴나요?**
정제 규칙을 고쳐도 사이트에 다시 요청하지 않고 raw에서 다시 만들 수 있고, 이상한 값의 원인을 원래 응답에서 추적할 수 있기 때문이다. 이번에 카테고리 규칙을 바꿨을 때 `clean --rebuild`로 사이트 요청 없이 68건을 다시 정제했다(6.3절).

**Q3. 중복은 무엇을 기준으로 판단하나요?**
전기신문 기사 번호(`idxno`)다. raw 단계에서는 (수집 방법, 기사 번호, 내용 해시)가 같으면 저장하지 않는다. clean 단계에서는 같은 기사 번호가 이미 있으면 중복 정책을 적용한다. 같은 실행 안에서 RSS와 크롤링으로 들어온 같은 기사는 먼저 하나로 합친다(본문·카테고리는 크롤링 값 우선).

**Q4. skip과 upsert는 어떻게 다르고 언제 쓰나요?**
skip은 처음 정제한 값을 그대로 두고 새 raw를 `duplicate`로 표시한다. 결과가 바뀌지 않아야 할 때(기본값) 쓴다. upsert는 새 값으로 갱신하되, 이미 있는 본문이나 사이트 카테고리를 빈 값으로 덮어쓰지 않고 요약도 유지한다. 기사 수정 내용을 반영하고 싶을 때 쓴다.

**Q5. 과제는 config.json으로 API 키를 관리하라는데 왜 .env에 두나요?**
config.json은 팀이 공유하고 저장소에 올리는 파일이라 키 값을 두면 노출된다. 그래서 config.json에는 키를 읽을 환경변수 이름을, 값은 `.env`(저장소 제외)에 둔다. 과제의 "환경변수 또는 설정 파일로 관리"를 둘 다 쓰는 방식이다(4.6절).

**Q6. AI가 JSON이 아닌 답을 주면 어떻게 되나요?**
응답에서 코드펜스와 앞뒤 설명을 건너뛰고 첫 JSON 객체를 찾는다. 없거나 필수 키가 빠졌으면 "JSON만 다시" 문구를 붙여 다시 요청한다. 한 건당 3번까지 시도하고, 그래도 안 되면 `ai_errors`에 기록하고 다음 기사로 넘어간다.

**Q7. `max_tokens`를 왜 보내지 않나요?**
`gemini-3-flash`는 답을 쓰기 전에 생각하는 데 쓰는 토큰도 `max_tokens`에 포함한다. 그래서 값을 작게 주면 답이 잘리거나 비어 버린다. 길이는 프롬프트("3문장 이내, 300자 이내")로 제한한다.

**Q8. AI가 기사에 없는 내용을 지어내면요?**
프롬프트 양쪽에 "주어진 기사에 없는 사실·수치는 쓰지 않는다"를 넣었다. 분석에서는 모델이 준 근거 기사 ID 중 입력에 없는 번호를 버린다. 리포트에는 근거 기사의 제목과 링크를 함께 실어서 읽는 사람이 원문으로 확인할 수 있게 했다. 다만 요약 문장 하나하나가 정확한지 자동으로 검증하지는 않는다(10절).

**Q9. 왜 SQLite이고 왜 공식 SDK가 아니라 requests인가요?**
SQLite는 표준 라이브러리이고 파일 하나라 설치가 필요 없으며, 조건 조회·중복 키·집계를 SQL로 바로 할 수 있다. requests는 기관 API가 지원하지 않는 옵션(`response_format`)을 피하고 `max_tokens`를 빼는 등 요청 본문을 직접 정하기 위해 썼다.

**Q10. 품질 지표 중 무엇이 가장 중요한가요?**
수집 성공률과 요약 완료율이다. 앞의 것은 사이트 요청이 제대로 되는지, 뒤의 것은 리포트의 키워드 TOP N과 AI 분석이 기사 전체를 반영하는지를 보여 준다. 평균 압축률은 요약이 너무 길거나 짧지 않은지 보는 보조 지표다.

**Q11. 카테고리별 기사 수 차트는 처음부터 지금 모양이었나요?**
아니다. 처음에는 카테고리마다 최신 5건씩 받아서 막대가 모두 5였다. 이렇게는 분야별 기사량을 비교할 수 없어서 기간 기준 수집(`--since`)을 더했다(4.4절).

### 9.2 "만약 ~라면"

**Q12. 만약 전기신문 페이지 구조가 바뀌면?**
페이지 해석은 `news_cli/collect/crawler.py` 한 파일에만 있다. 목록에서 기사를 못 찾으면 WARNING을 남긴다. 기사 본문을 못 찾으면 raw에는 저장하고, clean에서 RSS 요약문으로 대체하거나 `no_body`로 표시해 요약 대상에서 뺀다. 프로그램은 멈추지 않는다. RSS 수집은 그대로 동작한다. 고칠 때는 새 페이지를 본뜬 샘플(`tests/fixtures`)로 테스트를 먼저 바꾸고 선택자를 고친다.

**Q13. 만약 사이트가 요청을 막거나 robots.txt가 바뀌면?**
매 실행마다 robots.txt를 새로 읽고 금지된 경로는 요청하지 않는다. robots.txt를 읽지 못하면(5xx·연결 실패·401·403) 그 실행에서는 아무 요청도 하지 않는다. 429는 기다렸다가 재시도하고, Crawl-delay가 2초보다 길면 그것을 따른다. 요청 간격은 config의 `http.request_delay_sec`로 늘릴 수 있다.

**Q14. 만약 API 키가 유출되면?**
키는 `.env`에만 있고 코드·config·로그·DB·출력 파일에는 없다. 그러니 저장소나 결과물로는 새지 않는다. 그래도 유출됐다면 기관 콘솔에서 재발급받아 `.env`만 바꾸면 된다(코드 수정 없음). 옛 키로 호출하면 401이 나서 명령이 바로 멈춘다.

**Q15. 만약 AI 사용량이 모자라거나 API가 느려지면?**
`summarize --limit N`으로 나눠 실행할 수 있다. 이미 요약된 기사는 건너뛰므로 같은 기사에 사용량을 두 번 쓰지 않는다. 본문은 4,000자로 자르고, 분석에는 본문이 아니라 요약을 넣는다. 응답이 90초를 넘기면 타임아웃으로 재시도하고, 3번 실패하면 기록하고 다음 기사로 넘어간다. report·export·list·show는 AI 없이 동작한다.

**Q16. 만약 기사가 수만 건으로 늘면?**
`clean_news`에는 발행일·카테고리·상태 인덱스가 있어서 조건 조회는 그대로 빠르다. 분석은 조건마다 최신 40건(`--max-articles`)의 요약만 넣으므로 입력 크기가 일정하다. 대신 기간을 나눠 여러 번 분석해야 전체를 볼 수 있다. 요약은 기사마다 커밋하므로 `--limit`로 나눠 돌려도 이어서 진행된다.

**Q17. 만약 뉴스 소스를 하나 더 추가하라면?**
config의 `source` 설정과 `news_cli/collect/`의 해석기를 새 소스용으로 더하면 된다. clean 이후 단계는 테이블만 읽으므로 바꾸지 않아도 된다. 다만 지금 기사 키는 전기신문 기사 번호라서, 소스가 여럿이면 키 앞에 소스 이름을 붙여야 번호가 겹치지 않는다. `fetch --source` 옵션은 그 자리로 만들어 두었다.

**Q18. 만약 같은 기사가 수정되어 다시 올라오면?**
내용이 바뀌면 해시가 달라져 새 raw가 저장된다. clean은 정책에 따라 처리한다. skip이면 처음 값을 유지하고, upsert면 수정 내용으로 갱신한다(요약은 유지, 필요하면 `summarize --id N --force`).

**Q19. 만약 실행 도중에 멈추면(Ctrl+C, 네트워크 끊김)?**
수집은 채널마다, 요약은 기사마다 커밋하므로 그때까지 한 일은 남는다. 다시 실행하면 이미 본문을 받은 기사와 이미 요약한 기사는 건너뛰고 나머지만 한다. Ctrl+C는 종료 코드 130으로 끝난다.

**Q20. 감성 분석과 정기 실행 안내는 왜 안 했나요?**
보너스는 list·show만 하기로 범위를 정했다. 같은 시간을 필수 요구사항의 검증과 오류 처리 확인에 썼다. 대신 fetch·clean·summarize는 여러 번 실행해도 결과가 겹치지 않도록 만들었다(같은 조건 재수집 시 새 raw 0건, 실행 기록 5절).

| RSS 섹션 피드에는 최신 20건만 실린다 | 기간을 길게 잡으면 10개 카테고리 밖 기사(`기타`)는 다 모이지 않을 수 있다(10개 카테고리는 목록 크롤링으로 다 받음) | 기타 기사가 속한 사이트 분류의 목록도 크롤링 |
| 카테고리 키워드는 제목에서만 찾는다 | 회사 이름 속 낱말도 걸린다(예: '원광전력' → 전력) | 본문 앞부분까지 보거나 AI 요약 키워드 활용 |
| 분석은 조건마다 최신 40건까지만 넣는다 | 68건 전체 조건 분석은 최신 40건 기준이다(리포트에 실제 기사 수 표시) | 기간을 나눠 분석한 뒤 다시 종합 |
| 요약의 사실 정확성을 자동 검증하지 않는다 | 요약에 틀린 내용이 있어도 바로 알 수 없다 | 요약 속 수치가 본문에 있는지 확인하는 검사 추가 |
| 수집일 기준 추이는 여러 날 실행해야 의미가 있다 | 한 번만 실행하면 수집일 선이 하루에만 찍힌다 | 날마다 실행해 누적 |
